interviewQuestions:
  - prompt: Why is hash map lookup described as expected O(1) rather than O(1)?
    answer: >-
      The bound assumes a hash that spreads keys well, a bounded load factor, and
      constant-cost hashing and equality checks. Under those assumptions the
      expected number of keys compared per lookup is constant. Collisions can still
      put many keys in one bucket, so the worst case is O(n), and long keys take
      time proportional to their length to hash or compare.
    followUps:
      - What happens if every key lands in the same bucket?
  - prompt: What is a collision, and how do chaining and open addressing handle it?
    answer: >-
      A collision is two different keys mapping to the same bucket. Chaining keeps
      several entries per bucket and compares keys within it. Open addressing keeps
      one entry per slot and follows a defined probe sequence to other slots until
      it finds the key or an empty slot. Both still compare keys for equality.
    followUps:
      - Why does open addressing need special handling for deletion?
  - prompt: Why must a hash table compare keys after hashing?
    answer: >-
      Different keys can produce the same hash or bucket index, so reaching the
      right bucket does not prove the key matches. Equality confirms it. A table
      that trusted the hash alone would return or overwrite the wrong entry when
      keys collide.
  - prompt: What is the load factor, and why do hash tables resize?
    answer: >-
      The load factor is entries divided by buckets. As it rises, buckets hold more
      entries and lookups compare more keys. Growing the bucket array and
      redistributing entries keeps the load factor bounded. A resize costs O(n) when
      it happens, but spread over a sequence of insertions it keeps insertion
      amortized expected O(1).
    followUps:
      - Why do implementations grow the bucket array geometrically?
  - prompt: When is a hash map the wrong choice?
    answer: >-
      When you need keys in sorted order, range queries or the k-th smallest key, a
      hash map provides none of these; a sorted array or balanced tree may fit
      better. When keys are small dense integers, an array indexed by key can be
      simpler. JavaScript `Map` keeps insertion order, which is not sorted order.

## From positions to keys

An [array](/learn/dsa/arrays/) connects a position to a value. Suppose you want a
count for the word `array` rather than the value at position 2. A map connects
each **key** to a **value**; setting an existing key replaces its value.

A textbook hash table computes a hash from a key, maps it into a bucket range,
and looks for that key within the chosen bucket or probe sequence. The bucket
index uses array-style indexed access, but the hash table must still compare
keys. The array lesson's O(1) access alone does not prove O(1) key lookup.

## A collision does not mean equality

Two distinct keys can map to the same bucket. This is a **collision**, not a
duplicate key. A chained hash table keeps multiple entries per bucket and checks
key equality to find the right one. Open addressing instead searches other slots
using a defined probe sequence. You do not need to implement either strategy yet.

More entries per bucket usually mean more comparisons. Growing the bucket array
and redistributing entries can keep the load factor (entries / buckets) bounded,
at the cost of occasional O(n) rebuilds. With well-distributed hashes, bounded
load, and constant-cost hashing/equality, a typical hash table provides expected
O(1) lookup and amortized expected O(1) insertion. Collisions can make a worst-case
operation O(n). Large string keys also cost time to hash or compare.

<Callout title="JavaScript Map is an interface guarantee">
  ECMAScript requires average access time sublinear in the collection's size. It
  allows hash tables or other suitable mechanisms; it does not require strict
  O(1) operations or a specific collision strategy. `Map` also preserves key
  insertion order when iterating.
</Callout>

## Choose the lookup you need

Use an array for ordered positions and scans. Use a map when the central operation
is lookup or update by a meaningful key. A map does not automatically provide
sorted keys, range queries, or cheap access to “the third entry.”

Check yourself: why must a hash table compare the actual key after computing a
bucket? What could go wrong if it assumed that equal hashes meant equal keys?

## Two-minute recap

- A map answers **key → value** rather than **position → value**.
- Hashing narrows where to look; equality still establishes the matching key.
- Collisions are normal. Distribution, load and key costs affect performance.
- Expected, amortized and worst-case costs describe different things.
- JavaScript `Map` promises average sublinear access and insertion-order iteration,
  not a mandatory hash-table representation.

Revisit [array indexed access](/learn/dsa/arrays/#why-indexed-access-is-constant-time)
and explain how a bucket array helps a hash table without eliminating collisions.
