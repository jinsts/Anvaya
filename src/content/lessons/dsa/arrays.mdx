## A position is a useful promise

Imagine storing the last four temperature readings: `[12, 24, 36, 48]`. You want to
read the third reading, replace a faulty value, or process readings in order. An
array gives each value an **index**: a position counted from zero.

The third reading is at index `2`. Its value is `36`. The index is a position,
not a permanent identity: inserting a new reading before it changes its index.

Think of a row of numbered lockers. A locker number takes you straight to a slot;
finding the locker containing a particular item may require opening them all.
The analogy stops at insertion: a packed array must move values to make a gap.

**Predict:** Does knowing that `36` is present tell you its position? Not unless
you kept an index or searched. Knowing a position and finding a value are different jobs.

## Why indexed access is constant time

In a simplified fixed-width, contiguous array, a base address tells us where the
first cell lives. Every cell occupies the same width, so:

```text
address(i) = base + i × cellWidth
```

With base `1000`, width `4` bytes and index `2`, the address is `1008`. Computing
that address does not walk past indices 0 and 1. Under the usual unit-cost RAM
model, that calculation and the access take **O(1)** time, independent of length.

<IndexedMemory />

The model assumes constant-time address arithmetic and fixed-width stored values
or references. Real memory has caches, alignment and allocation constraints; O(1)
does not mean identical latency on every access. If cells store references, the
referenced objects need not sit next to one another.

<Callout title="A model, not a JavaScript memory guarantee" variant="warning">
  JavaScript `Array` is a language-level object with special indexed-property
  and `length` behavior. It can be sparse and hold mixed values. ECMAScript does
  not promise contiguous storage or a specific Big-O bound for these operations.
  The diagrams and cost table teach a dense textbook array; engines choose their
  own representations. Typed arrays provide typed views over buffers, a separate
  abstraction.
</Callout>

## Explore the work behind an operation

Start with `[12, 24, 36, 48]`. **Predict what must move to insert `30` at index `2`.**
Prepare the operation, then use **Next step**. The initial capacity is full, so
this example deliberately includes both growth and shifting.

<ArrayExplorer client:visible />

The same insertion in words:

1. Four occupied cells fill capacity 4. Allocate capacity 8 and copy the four values.
2. Shift `48` from index 3 to 4, then `36` from index 2 to 3. Moving right to left
   keeps the unread values safe.
3. Write `30` into index 2. The logical array is `[12, 24, 30, 36, 48]`: length 5,
   capacity 8. The other three cells are unused.

Reading index 2 does one indexed access. This middle insertion shifts a suffix
and, here, also copies the old buffer. The two jobs have different costs.

Try these variations before reading on:

- Reset, then **read** index 2. No values move.
- **Update** index 2 to 99. Length stays the same; the old value is replaced.
- **Append** 60. It writes at the old length; if capacity is full, copying happens first.
- **Remove** index 1. Later values move left; our model retains capacity.
- Load a blank example and insert at index 0. Try reading the empty array and explain the error.
- Insert at index `length`, then try index `length + 1`. Only the first is valid here.

No animation or timing is required. Every intermediate state is explicit; reset
cancels an unfinished trace and restores the deterministic initial values.
The explorer saves snapshots for teaching. Its rendering and trace-storage costs
are separate from the algorithmic costs shown in the operation explanation.

## Length, capacity, and the occasional expensive append

A **fixed-size array** has a set number of slots. A **dynamic array** keeps a
backing array and a logical length. Only indices `0` through `length - 1` contain
logical values. The invariant in a finished operation is:

```text
0 ≤ length ≤ capacity
```

Appending with spare capacity adds one value and increases length. Appending to
a full buffer needs another allocation and a copy. Our model doubles capacity:
`4 → 8 → 16`. A resize from capacity 4 copies four old values before writing the fifth.

Why is append called **amortized O(1)**? Across m appends starting empty with
constant initial capacity, copies happen at geometrically increasing sizes.
Their sum is less than a constant multiple of m; adding the m writes still gives
O(m) total work. The cost per append, spread over that whole sequence, is O(1).
This bound assumes allocation/initialization of k cells costs O(k).

That is a bound over a sequence, not a probability or a guarantee for the next
append. A particular append that resizes still takes O(n) time and temporarily
needs both buffers. Adding only one slot on each resize would instead copy on
every append and accumulate quadratic work. Middle insertion still shifts values,
so doubling does not make arbitrary insertion amortized constant time.

We keep capacity after removal to isolate shifting from shrinking. A production
container may shrink with a carefully chosen policy; shrinking immediately after
every removal can cause repeated allocations. The explorer caps examples at 16
values for readability, not because arrays have that limit.

For insertion, the loop invariant is that the suffix already visited has moved

## Count the work, then name the bound

Let `n` be length before an operation and `i` its index. Count reads, writes, and
comparisons before reaching for Big-O. Insert at index 0 shifts n values; insert
at n shifts none. With no resize, these cost O(n) and O(1), respectively.

<ComplexityTable />

“Average” needs an input distribution; “amortized” needs a sequence of operations.
Neither term means that a slow operation cannot happen. Big-O is an upper bound;
Θ gives a tight asymptotic bound under the stated model.

## Choose arrays for the work you have

Arrays are a good fit for ordered readings, image pixels, lookup by known position,
and repeated sequential processing. A dense contiguous representation often has
good memory locality, though that observation is not a JavaScript layout promise.

If your main question is “what value belongs to this key?”, a
[hash map](/learn/dsa/hash-maps/) may avoid repeated scans. With a linked list,
insertion after an already-known node can take O(1), but finding an arbitrary
position takes O(n); each node also needs link storage. Neither alternative makes
all operations cheap. Choose based on the operations you actually repeat.

Two useful patterns to study later are **two pointers** (move two positions through
a sequence, such as inward when checking a palindrome) and a **sliding window**
(reuse information while a contiguous range moves, such as a rolling sum). These
are future lessons, not prerequisites here.

### Pitfalls worth catching early

- **Off by one:** the last occupied index is `length - 1`; `length` is a valid insertion position only.
- **Mutation:** two variables can refer to the same array. A change through one is visible through the other.
- **Empty input:** a length-zero array has no readable index. Decide the contract before coding.
- **Holes:** `delete values[i]` leaves a hole; it does not shift values or decrement length.
- **Equality:** `===` compares objects by identity, not by matching their properties. `NaN === NaN` is false; the labs constrain inputs to finite numbers.
- **Cost assumptions:** a method name does not prove constant time. Scanning, shifting, copying, allocation and the cost of comparing large values all matter.

## Two-minute recap

- **Position → value:** a known index enables O(1) indexed access in the fixed-width RAM model.
- **Value → position:** without an index, an unsorted search may inspect all n values.
- **Preserve order:** insertion shifts a suffix right; removal shifts it left. Direction matters.
- **Length is not capacity:** values occupy `[0, length)`; capacity describes available slots.
- **Growth moves the bill:** doubling gives amortized O(1) append, but a resize is O(n).
- **Model is not runtime:** JavaScript does not guarantee a contiguous representation for ordinary arrays.
